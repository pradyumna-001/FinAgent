## Decisions made

- **interrupt() re-executes the node body from the top on resume** — proven experimentally (probe: prints/counter before `interrupt()` run twice, after runs once), then confirmed in `langgraph.types.interrupt` source ("The graph resumes from the start of the node, re-executing all logic"). Rule derived: pre-interrupt = pure reads/guards only; post-interrupt = side effects.
- **No clean public "am I resuming?" API exists** — checked the source (`scratchpad.resume` is private machinery). So the duplicate-`started`-event problem was solved by *not emitting started at all*: gate emits context via the interrupt payload at pause, `agent_completed` on resume only. More truthful event model for a node that is, by definition, waiting.
- **Fail-visible severity criterion, restated (again, correctly this time):** "can it be fixed?" is *not* severity. Guard FATAL is justified because interrupting with no row would hang the pipeline invisibly. Blast radius + visibility.
- **Trusted-boundary rule for SQL:** values from the network go through bound parameters even when validated (`:decision`); the f-string `SET LOCAL` survives only because `int()` cast makes injection impossible — flagged as tech debt regardless.
- **`create_graph()` in pipeline.py is broken-and-never-called**: `async with AsyncPostgresSaver.from_conn_string(...)` closes the connection at `return`, so the compiled graph holds a dead saver. Zero callers in `app/` — latent until approval_gate made checkpoints load-bearing.
- **Design call (senior-guided, mine to implement):** lifespan-owned saver per process (Option B), not per-call context manager. Worker owns a saver+compiled graph; poller owns its own saver+graph; `thread_id = pipeline_run_id` is the join key across processes (it's already the callback payload via `decode_callback`).
- **Partial-migration recovery** (manual `ALTER` + `alembic stamp`) is dev-only acceptable; CI/fresh DBs must run `1789584853` clean — integration tests will prove it.
