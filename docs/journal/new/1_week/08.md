## Architectural decisions made today

1. **`SET LOCAL` uses f-string, not bind params.** Documented as a
   foot-gun: if anyone changes the type annotation to `str`, the
   f-string becomes injection. Defense today is two layers (Pydantic
   type + `int()` cast). The PR description documents this so the
   next reader doesn't innocently remove the cast.

2. **`WHERE manager_id = :mid` kept even though RLS already filters.**
   Belt-and-suspenders. RLS could be disabled in a misconfigured role
   or admin debug session; the WHERE still filters. Cost is microseconds.

3. **Bilingual boundary dissolved for now.** User decision to use
   English (`manager-id`) everywhere. Issues doc deferred translation
   to its own session. The PR body explicitly flags the spec mismatch
   so a reviewer can challenge it.

4. **Adjacent fix (`alembic/env.py`) is in-scope for #04b.** Reasoning:
   the route couldn't be verified without it, and PR #30 already
   promised the env.py refactor. We accelerated it rather than file
   a follow-up. The remaining #03b work (role split, `finagent_app`
   user) is still a separate issue.

5. **Tests are the source of truth for the reset behavior.** The unit
   test asserts ContextVars are `None` after every request — that's
   the only thing proving the `finally` reset is wired. Without this
   test, the reset could be removed and no human review would catch it
   until production logs started carrying wrong correlation IDs.

6. **The Socratic discipline matters more than the code.** Multiple
   times today the user said "I don't know" or gave shallow answers.
   Stopping to teach (ContextVar theory, async vs sync engines,
   `SET LOCAL` semantics) before each chunk was the right call. The
   user types the code; they understand *why* it works.

## ContextVar theory brief (for future reference)

Three things worth keeping in mind whenever ContextVars appear:

1. **Why ContextVar and not module variable:** async coroutines
   interleave at every `await`. A module variable shared across
   coroutines would be a thread-safety bug equivalent — one request's
   middleware overwriting another's. ContextVar gives each coroutine
   its own copy, derived from the context it was created in.

2. **`create_task` snapshots:** the new task inherits the parent's
   ContextVar values at the moment of `create_task`. Parent's later
   mutations don't propagate; child's mutations don't leak back. We
   don't have background tasks yet, but #04c will — when it does,
   this snapshot behavior means the SSE task sees the request's
   pipeline_run_id automatically.

3. **Reset failure mode:** if `reset(token)` is missing in `finally`,
   the ContextVar stays at its set value for the rest of the worker
   process. Subsequent requests reuse the worker; their logs all
   carry the wrong correlation ID. The bug is silent — logs look
   correct, just cross-contaminated. This is the test
   `test_correlation_headers_set_contextvars_during_request` is
   catching: asserting the value is `None` after every request.
