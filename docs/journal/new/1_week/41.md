## The probe that corrected the tutor — third time

I came to `scratch_ghost_probe.py` claiming it would change the tutor's mind about the rollback-fixture question. It did. Tutor said: resume on a thread with no checkpoint "fails with a missing-checkpoint error." The probe proves otherwise:

```
before: {} ()              ← fresh thread: nothing there
after: {} ('gate',)        ← values STILL empty, next=('gate',) — parked!
{'__interrupt__': [...]}   ← first ainvoke returned an INTERRUPT payload, not the resume value
{'value': 'approved'}      ← second ainvoke: now the resume landed
```

**Resume on an unknown thread does not error — it silently starts a fresh run from START, swallows the resume value, re-executes everything, and re-parks.** The ghost is real, and it's worse than a ghost checkpoint: persist + send + gate all re-run — ghost recommendation row, ghost telegram send, lost operator decision. The tutor's Horn A failure mode was wrong; Horn B (rollback theater — the saver commits on its own connections) still stands, because InMemorySaver can't model connection management. Journal 40 said to delete this file in pre-PR hygiene — it earned its keep first. The finding is banked in the plan doc.

## What I learned about the fixture strategy

- **A mock is valid when the seam it replaces is irrelevant to the behavior under test.** `test_graph_pipeline.py` mocks the checkpointer away — fine for reducer/merge/fail-visible assertions, but §4 asserts resume and exactly-once: the seam IS the behavior. You can't fake the thing you're asserting on.
- **Rollback fixtures are dead for §4 — both horns:** trap the writes → silent ghost re-run (proven above); let them commit → the saver's own-connection commits make rollback theater — it cleans nothing the graph wrote. Reuse the conftest pattern instead: testcontainers = fresh container per *session*, migrations once, isolation by unique `thread_id` per test. My "per-test fresh DB" guess was the wrong granularity for this repo — the conftest already answers it.
- **Resume does not "execute everything from top"** — completed nodes stay completed, restored from the checkpoint. Only the interrupted node re-executes, and `interrupt()` returns the resume value instead of raising. My first answer conflated these; the probe's second invoke showed the real thing.

## Findings from plan reconnaissance (all in the plan doc)
