## Decisions made

- **`frozen=True` gives hashability for free** — future `set()`-based dedup of `state["flags"]` works without custom `__hash__`. Trade-off: mutation path is gone, but flags should be records-of-observations, not state objects.
- **`.value` (lowercase "info"/"warning"/"fatal"), not `.name`** — `.value` is the wire format; renaming the Python enum member later doesn't break stored JSONB values.
- **Naive `datetime.now()` default** — whole module is naive-by-default. Mixing naive and aware raises `TypeError` on comparison, so the choice is module-wide. UTC-awareness is a one-grep migration if needed later.
- **No `is_info()` method** — YAGNI; no caller branches on INFO.
- **`__post_init__` uses two separate `if not x: raise` blocks** — each error message specific to its field; self-documenting contract.
- **No conftest, no shared test helpers** — locality beats DRY when duplication is <5 lines/test and the duplicated content is the thing being tested.
- **2 commits, not 1** — matches #05a's pattern (one feat + one test). Within the Rule 2 smell range (3–10).

## Socratic questions from this session

### `app/utils/flags.py`

1. **Why is `.to_dict()` better than accessing `.created_at` directly?**
   `.to_dict()` controls the *serialization boundary*. `__dict__` is Python's internal layout — coupling JSON output to attribute names means renaming `created_at` to `_created_at` or adding a memoized property silently breaks JSONB rows. `.to_dict()` is the dataclass's explicit contract: rename a field, update `to_dict()` in one place, downstream is unchanged. The JSONB column has no idea what `Severity` or `datetime` are; `.to_dict()` is where the conversion to `str` / ISO-8601 lives.

2. **Why does `frozen=True` matter for hashing/deduping?**
   `frozen=True` generates `__hash__` from the fields automatically. A mutable dataclass has `__hash__ = None` — can't go in a `set` or be a `dict` key. Future dedup like `state["flags"] = list(set(existing + new))` works without writing a custom `__hash__`. Equality-by-value (same source + severity + message = same flag) comes free.

### tests/unit/test_dataflag.py

3. **Why `pytest.raises(match=...)` instead of `try/except` + manual assert?**
   `try/except` silently passes if no exception is raised, then fails at the next line with a confusing error. `pytest.raises` reports `"DID NOT RAISE <class 'ValueError'>"` immediately, pointing at the right line. `match=` ties the assertion to the *specific* error contract — a `ValueError` from somewhere else (e.g., a future field validator) won't satisfy it. Self-documenting: "this code raises ValueError with this message about source."

### `.github/workflows/ci.yml`

4. **Why `on.push.branches: ["**"]` instead of bare `on.push`?**
   Bare `on.push` fires on tags too. `["**"]` is "any branch, no tags." Tags are typically release flows; CI shouldn't trigger on them.

5. **Why `cache-dependency-glob: "uv.lock"` only, not `pyproject.toml` too?**
   The lockfile is the resolved truth — it changes when *any* dep (direct or transitive) updates. Hashing `pyproject.toml` alone misses transitive changes. uv's resolver reads both files anyway; the lockfile is the authoritative cache key.

6. **If mypy fails, does pytest still run?**
   No. Steps run in order; a non-zero exit marks the step failed and skips subsequent steps. Whole job is marked failed. That's the desired behavior — broken types block the merge before the test suite burns time.

### test_correlation.py refactor

7. **Why does building a tiny Starlette app mean we don't need `DATABASE_URL`?**
   The original test imported `app.main`, which transitively imports `app.db.session`, which constructs `Settings()` at module import time. `Settings` requires `DATABASE_URL` and `MIGRATION_DATABASE_URL`. Building a Starlette app with only `CorrelationMiddleware` skips the entire DB config chain — nothing in the middleware touches the database.

8. **What part of `app.main` was actually being tested?**
   Only the `CorrelationMiddleware`. The fact that the test imported the whole app was accidental, not intentional — the middleware gets mounted by `app.main`, but mounting order and FastAPI-specific behavior weren't under test. A unit test should test the smallest unit that proves the contract.

9. **If we wanted to assert the middleware works in the real FastAPI app, where would that test live?**
   `tests/integration/`. Unit tests prove a component in isolation; integration tests prove it composes correctly with other components. The middleware-alongside-other-stacks case (alongside auth, logging, error handlers) is integration territory and needs the full app + DB.
