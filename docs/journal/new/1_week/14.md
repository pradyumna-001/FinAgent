## What happened today

- Found a real bug in the untracked migration: `recommendations` policy joined `portfolios` instead of `morning_notes`. Fixed.
- Added `WITH CHECK` to all four new isolation policies + retroactively to the existing `morning_notes` policy. Without it, a manager can rewrite `manager_id` on a row they own and steal it.
- Wrote 6 new probes (5 visibility + 1 behavioral). The behavioral probe attempts a cross-tenant INSERT and asserts Postgres rejects it.
- Refactored `tests/conftest.py` to be idempotent — the old fixture only worked for single-test runs.

## Decisions made

- **`recommendations` joins `morning_notes`, not `portfolios`** — `Recommendation` has no direct `manager_id`; the chain is `recommendations → morning_notes.manager_id`.
- **`WITH CHECK` everywhere an isolation policy exists** — `USING` blocks reads, `WITH CHECK` blocks writes that would mutate the isolation key. Both are required.
- **Behavioral probe expects `InsufficientPrivilegeError`** — Postgres uses SQLSTATE 42501 for RLS violations (same class as `GRANT` failures, by design). Catching the actual class gives a precise signal.
- **Fixture uses `SELECT FROM (VALUES ...) AS v(...) WHERE NOT EXISTS`** for tables without a matching unique constraint — `ON CONFLICT (id) DO NOTHING` alone doesn't catch natural-key duplicates when ids are auto-generated.

## Decisions worth flagging

- **`morning_notes` has no natural-key uniqueness** — `(portfolio_id, note_text)` should probably be `UNIQUE` via a future migration. The fixture's `WHERE NOT EXISTS` keeps the *test* idempotent but production code can still duplicate rows.
- **`split('@', 1)` in conftest URL parsing** — works for the current password but breaks if it contains `@`. Worth flagging for whoever next touches auth fixtures.
