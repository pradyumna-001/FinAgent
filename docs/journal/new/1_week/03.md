## What changed in the skill
The Closed-Issue Peer Review section of `junior-step-by-step-coder/SKILL.md`
should be updated with the lessons from this session. Five lessons:

1. **Post questions on PR via `gh`, defend in chat.** The colleague
   role is public; the user types the defense into the PR comment
   themselves. Do not write the user's answer for them.
2. **Every question anchors to `file:line` of the actual diff.** If a
   line is referred to in multiple places, pick the first reference.
   Verify the diff-position matches the file-line before posting.
3. **Use inline review comments, not top-level PR comments.** They
   land in the "Files changed" tab alongside the code, mirroring what
   a teammate would do. Top-level wrapper comments are only for
   framing or summary, not questions.
4. **Teammate phrasing, not exam-style phrasing.** "Walk me through
   the contract" beats "two or three sentences, no code." The
   curiosity posture reads naturally; the exam posture does not.
5. **Do not write the user's answers.** This slipped once in this
   session — Q2 was overwritten with my version of the defense. The
   rule: I only post *questions*. The user posts their own answers
   in chat first, then mirrors them onto the PR (or asks me to
   mirror exact text).
6. **OS-shell quirk on Windows.** `gh api` rewrites starting slashes
   into filesystem paths when called from a repo workdir. Run
   `gh api` from `C:/Users/.../AppData/Local/Temp/opencode` (the
   pre-approved temp dir) to avoid the path-rewrite.
7. **Resolution pass = per-comment mark ✅ Solved or follow-up.**
   Mechanism that's been used in this session: read the user's
   posted replies via `gh api .../comments?q=author`, then post the
   resolution judgment as PR-level comments tying to each Q-number
   (inline `resolved=true` only works after a review is submitted;
   during an open review thread, post a sibling PR comment).
